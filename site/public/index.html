ZenoFCIS: a proposer suggests, a judge decides

The account-lockout example application, running in this page through its own commit authority, with an in-memory shell in place of SQLite.

Proposers, judges, and the shell

A proposer suggests a decision. It may be an AI agent, a synthesized core, or hand-written code; here it is the example's hand-written program.

The judge is the commit authority with its laws. It admits the request against the schema, runs the program, evaluates every law that applies to the decision, and mints an authorization only for a decision that satisfies them. A decision that breaks a law is never authorized, so it never reaches a shell.

The imperative shell only persists and delivers. On a server it is SQLite with an outbox; in this page it is the library's in-memory reference shell, which the authority itself checks before each publication.

What runs here is the account-lockout template exactly as zeno-fcis new writes it, built for WebAssembly without its SQLite shell. Its authority, program, and law checker are the same source that decides on a server. The page only supplies each request and its context, including the time, and shows what the authority returned. After loading, the page makes no network requests.

Account lockout

Three consecutive failed logins lock the account for 900 seconds. A failed login is a committed failure: the login fails, but the attempt is recorded. Every request carries its time, and the decision never reads a clock. Only a request marked admin may unlock. Alerts leave through the outbox. The rules, in the order they apply, are in the template's README, copied here as shipped (crates/zeno-fcis-cli/templates/account-lockout/README.md in the repository).

What is checked, and at what strength
  • Laws 500 to 503, written in project.zeno, are evaluated at run time on every decision before it can be published; law 509 is the framework's rule that a rejection publishes nothing. The panel shows each law's status as the evaluation reports it.
  • The template's own tests, which run on a host and not in this page, compare the executed application with a reference model of the README's rules on 20 examples and 606 grid inputs, give the law checker faulty decisions to refuse, and probe determinism.
  • Claim 600 states that the action laws alone keep the lock invariant. CVC5 answers unsat for its induction step over the declared integer ranges: that answer is attested, not proved. Z3's unsat is recorded as unsupported evidence, and there is no Lean export for inductive claims.
  • This module is checked by a headless replay (site/tests/replay.mjs) that runs the template's 20 decision examples and the README's demonstration through it and compares every outcome with the examples file and with the gate's expected summary.
  • The time and the admin flag are trusted page inputs, as the README says of its own context: a deployment must authenticate them before admission.
