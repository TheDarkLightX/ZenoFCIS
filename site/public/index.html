ZenoFCIS: a proposer suggests, a judge decides

The example applications, running in this page through their own commit authorities, with an in-memory shell in place of SQLite.

Proposers, judges, and the shell

A proposer suggests a decision. It may be an AI agent, a synthesized core, or hand-written code.

The judge is the commit authority with its laws. It admits the request against the schema, runs the program, evaluates every law that applies to the decision, and mints an authorization only for a decision that satisfies them. A decision that breaks a law is never authorized, so it never reaches a shell.

The imperative shell only persists and delivers. On a server it is SQLite with an outbox; in this page it is the library's in-memory reference shell, which the authority itself checks before each publication.

Each example below is a template exactly as zeno-fcis new writes it, built for WebAssembly without its SQLite shell. Its authority, program, and law checker are the same source that decides on a server. The page only supplies each request and its context, including any time, and shows what the authority returned. An example's module is fetched when its section is opened; after that the page makes no network requests.

Account lockout

Three consecutive failed logins lock the account for 900 seconds. A failed login is a committed failure: the login fails, but the attempt is recorded. Every request carries its time, and the decision never reads a clock. Only a request marked admin may unlock. Alerts leave through the outbox. The proposer is the example's hand-written program. The rules, in the order they apply, are in the template's README (crates/zeno-fcis-cli/templates/account-lockout/README.md in the repository).

What is checked, and at what strength
  • Laws 500 to 503, written in project.zeno, are evaluated at run time on every decision before it can be published; law 509 is the framework's rule that a rejection publishes nothing. The panel shows each law's status as the evaluation reports it.
  • The template's own tests, which run on a host and not in this page, compare the executed application with a reference model of the README's rules on 20 examples and 606 grid inputs, give the law checker faulty decisions to refuse, and probe determinism.
  • Claim 600 states that the action laws alone keep the lock invariant. CVC5 answers unsat for its induction step over the declared integer ranges: that answer is attested, not proved. Z3's unsat is recorded as unsupported evidence, and there is no Lean export for inductive claims.
  • This module is checked by a headless replay (site/tests/replay.mjs, run by site/build.py) that runs the template's 20 decision examples and the README's demonstration through it and compares every outcome with the examples file and with the gate's expected summary.
  • The time and the admin flag are trusted page inputs, as the README says of its own context: a deployment must authenticate them before admission.

Order fulfillment

One order from checkout to delivery. Payment and shipping happen in other systems: the order sends them requests through the outbox, and their answers come back as commands. Each request is numbered, so a provider can recognize a retry, and a callback that arrives twice or late is rejected and changes nothing. A declined payment is a committed failure: the order returns to Placed and keeps its attempt count. The proposer is the example's hand-written state machine. The rules, in the order they apply, are in the template's README (crates/zeno-fcis-cli/templates/order-fulfillment/README.md).

What is checked, and at what strength
  • Laws 500 to 506, written in project.zeno, are evaluated at run time on every decision before it can be published: 500 on every commit, 501 to 505 on accepts, 506 on committed failures; law 509 is the framework's rule that a rejection publishes nothing. In Rust, because formulas cannot see them: the rejection reason, the exact request, the absence of effects, and the genesis.
  • The template's own tests, which run on a host and not in this page, explore the application from genesis and find 20 reachable states, run 1,440 commands from them through admission, the authority, the program, the law checker, the committed patch, and the outbox against a reference model of the README's rules, compare 23 examples, give the law checker faulty decisions to refuse, and probe determinism on 400 inputs. All of these are detectors, in the README's words: agreement shows that these runs matched, not that the application is correct for every possible deployment. No claim is submitted to a solver.
  • This module is checked by the headless replay (site/tests/replay.mjs) that runs the template's 23 decision examples, each from an order reached from genesis, and the README's demonstration through it.
  • The caller is a trusted page input, as the README says of its own context: a deployment must authenticate each caller before admission.

Inventory reservation

The stock of one product: units are available to sell or reserved for an order; shipping sends reserved units out, and restocking brings units in. The decision core is synthesized: synthesis.json states the rules as a relation over every input, and zeno-fcis synth selected a program that satisfies it on all 432 of them. A conservation law keeps the count of units exactly right. The proposer is that synthesized step, behind a hand-written operator check. The rules are in the template's README (crates/zeno-fcis-cli/templates/inventory-reservation/README.md).

What is checked, and at what strength
  • The synthesized step: zeno-fcis synth run evaluates hole assignments over all 432 inputs and selects the first that satisfies the contract on every one. In the README's words, that selection is exhaustive verification against the contract, for the program as the library's interpreter runs it; synth verify replays the emitted Rust and Python on every input. It is only as right as the contract, which tools/check_synthesis.py compares with a separate restatement of the rules.
  • Laws 500 to 502 are evaluated at run time on every accepted decision before it can be published: the bounds, the conservation of units, and each action's exact movement; law 508 records that the application never commits a failure, and law 509 that a rejection publishes nothing. In Rust: the rejection reason, the exact shipment request, and the absence of effects.
  • The template's own tests, on a host, run all 864 admitted inputs through admission, the authority, the adapter, the law checker, the committed patch, and the outbox, check that all 36 states are reachable from genesis, compare 20 examples, give the law checker faulty decisions to refuse, and probe determinism on 216 inputs. For this finite domain the conformance test covers every decision the application can make; all of these are detectors. No claim is submitted to a solver.
  • This module is checked by the headless replay that runs the template's 20 decision examples, each from a stock reached from genesis, and the README's demonstration through it.
  • The operator flag is a trusted page input, as the README says of its own context.

Compliance gateway

Transfers screened for one customer by an expert system's rule base: rules.txt holds twelve prioritized rules over finite features, and every decision names the rule that fired. A blocked transfer is a committed failure that adds a strike; three strikes freeze the account until a reviewer reinstates it. Review tickets and block alerts leave through the outbox. The proposer is a step that zeno-fcis synth selected from the rule base, and the law checker evaluates the rule base itself as a second judge. The rules are in the template's README (crates/zeno-fcis-cli/templates/compliance-gateway/README.md).

What is checked, and at what strength
  • The rule base is checked over all 720 combinations of its features to be consistent, total, and live, and a rule base that fails is refused at build time. The synthesized step was selected on all 720 inputs and replayed by synth verify in Rust, Python, and JavaScript; in the README's words, that is exhaustive verification against the contract, which is only as right as its derivation from the rule base, checked by two evaluators that share nothing with the synthesizer.
  • Laws 500 to 503 are evaluated at run time on every decision before it can be published; law 509 is the framework's rule that a rejection publishes nothing. In Rust: the rule base itself, the kind of decision and its reason, the exact ticket or alert, the absence of effects, and a zero genesis.
  • Claim 600 states that the laws alone keep the strikes within their bounds, for every integer. CVC5 answers unsat for its induction step: that answer is attested, not independently checked, and not proved. Z3's unsat is recorded as unsupported evidence, and there is no Lean export for inductive claims. The step says something about this application only together with tests/claims.rs, which checks the base case, the observer, and the law manifest.
  • The template's own tests, on a host, run all 2,880 admitted inputs through admission, the authority, the adapter, the law checker, the committed patch, and the outbox, compare 28 examples that reach every rule, give the law checker faulty decisions to refuse, and probe determinism on 144 inputs. All of these are detectors. A restatement of the rule base in Tau Language has been run to completion on a six-input sample only; no agreement on the whole table is claimed.
  • This module is checked by the headless replay that runs the template's 28 decision examples, each from a standing reached from genesis, and the README's demonstration through it.
  • The identity tier, the reviewer flag, the amount band, and the risk rating are trusted page inputs, as the README says of its own context: a deployment must establish them before admission.

Withdrawal queue

One vault with two withdrawal lanes. Each lane's owner requests a withdrawal, and a keeper's tick pays at most one lane by following a checked controller. The tick's context carries an alarm; an honored alarm pauses payouts, but every requested withdrawal is still paid: alarms delay, they never freeze. Raise the alarm here and keep ticking to watch it. The proposer for ticks is a controller step that zeno-fcis synth selected; deposits and requests are hand-written rules. The rules are in the template's README (crates/zeno-fcis-cli/templates/withdrawal-queue/README.md).

What is checked, and at what strength
  • The controller step was synthesized and exhaustively checked against the tick rules on all 384 inputs, and replayed by synth verify in Rust, Python, and JavaScript. The table that step defines, with the vault's contract, was certified by OrbitSynthesis's checker for every input sequence: it printed ACCEPT over 26 reachable product states and 208 transitions, and rejected two wrong tables with a counterexample cycle each; tests/controller.rs re-checks it with an independent implementation of the same decision procedure. In the README's words, the liveness claim is a checked property of the finite model, not of the running application by itself; the refinement law connects each concrete tick to that model, tick by tick at run time, and it is not a machine-checked proof. The response bound is 8 ticks.
  • Laws 500 to 503 are evaluated at run time on every committing decision before it can be published; law 508 records that the application never commits a failure, and law 509 that a rejection publishes nothing. In Rust: the rejection reason, the exact payout request, the absence of effects, the genesis, and the refinement of each tick against the contract's transition table and the certified table's row.
  • Claims 600 and 601 state that the action laws alone keep the vault solvent and the pause in range, for every integer. CVC5 answers unsat for both induction steps: attested, not independently checked, and not proved. Z3's unsat is recorded as unsupported evidence, and there is no Lean export for inductive claims. tests/claims.rs checks the base case, the observer, and the law manifest.
  • The template's own tests, on a host, explore 420 reachable vaults and 3,360 decisions against a reference model of the rules, check that a requested withdrawal is paid within 8 ticks under every path in the grid, compare 26 examples, give the law checker faulty decisions to refuse, and probe determinism on 120 inputs. All of these are detectors.
  • This module is checked by the headless replay that runs 25 of the template's 26 decision examples, each from a vault reached from genesis, and the README's demonstration through it; the one example whose vault no sequence of requests reaches is named in the replay's output, and the template's conformance test decides it from the admitted vault.
  • The caller and the alarm are trusted page inputs, as the README says of its own context: the property checked says what the vault does with an alarm, not whether the alarm was right.

Agent treasury guard

A treasury that an AI agent trades for. The agent proposes swaps; its proposal is only a command, and the decision here is the guard. Whatever the agent proposes, the treasury never commits more than its daily budget, never drops below its reserve, never swaps outside the slippage bound against the oracle price, and never has more than one swap outstanding. Accepted swaps leave through the outbox as requests shaped after ZenoDEX's SwapIntent, and the DEX's settlements and failures come back as commands. Here the agent is scripted: a fixed list of proposals, good and bad, shown below as a proposer; no model is called. The proposer's core was selected by zeno-fcis synth over the guard's facts. The rules are in the template's README (crates/zeno-fcis-cli/templates/agent-treasury-guard/README.md).

What is checked, and at what strength
  • The decision core was synthesized on all 6,144 tuples of an action and the guard's eleven facts, and replayed by synth verify in Rust, Python, and JavaScript; in the README's words, that selection is exhaustive verification against the contract, for the program as the library's interpreter runs it. A small hand-written adapter computes the facts with checked arithmetic.
  • Laws 500 to 508 are evaluated at run time on every decision before it can be published: 501 and 502 on every commit, 503 to 507 on accepts, 508 on committed failures; law 509 is the framework's rule that a rejection publishes nothing. In Rust: the rejection reason, the exact request, the absence of effects, and the genesis.
  • Claims 600 and 601 state that the action laws alone keep the reserve, a non-negative base, the day's committed value within the budget, and the swap bookkeeping, for every integer. CVC5 answers unsat for both induction steps: attested, not independently checked, and not proved. Z3's unsat is recorded as unsupported evidence, and there is no Lean export for inductive claims. tests/claims.rs checks the base case, the observer, and the law manifest.
  • The template's own tests, on a host, decide 25,094 inputs against a reference model of the rules, including a search of everything one day can reach from genesis, along whose every path the accepted proposals commit at most the budget; compare 30 examples; give the law checker faulty decisions to refuse; and probe determinism on 864 inputs. All of these are detectors.
  • This module is checked by the headless replay that runs 29 of the template's 30 decision examples, each from a treasury reached from genesis, and the README's demonstration through it; the one example whose treasury no sequence of requests reaches is named in the replay's output, and the template's conformance test decides it from the admitted treasury.
  • The caller, the tick, the oracle price and its time, and the model identity are trusted page inputs, as the README says of its own context: a deployment must authenticate the caller, read its own clock and price feed, and bind the model identity from its own records before admission. The guard bounds what the treasury commits against the oracle price, not the market.
